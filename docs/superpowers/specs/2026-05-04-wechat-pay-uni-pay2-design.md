# 微信支付真实接入设计（uni-pay 2）

## 1. 背景

当前小程序充值链路已经具备以下业务基础：

- 前端充值页可展示点数套餐并发起下单。
- 业务订单表 `curtain_pay_order` 已经落地。
- 订单到账后加点、写点数流水的云函数逻辑已经存在。
- 自动化测试已经覆盖订单创建、到账幂等、订单列表三块核心业务行为。

当前缺口在于支付底座仍为模拟支付：

- `pages/profile/recharge.vue` 仍按 mock 支付分支处理。
- `curtain-pay-order-create` 只返回 `paymentParams.mock = true`。
- 未接入真实微信小程序支付下单、回调验签、查单能力。

本次目标是在尽量保留现有业务结构的前提下，接入官方推荐的 `uni-pay 2` 作为微信支付底座，完成真实微信支付链路。

## 2. 目标

本次接入完成后，系统应满足：

1. 用户在充值页选择套餐后，可拉起真实微信小程序支付。
2. 支付成功后，服务端按回调结果更新业务订单状态。
3. 支付成功后，用户点数账户自动到账，并写入点数流水。
4. 同一笔订单的重复回调不会导致重复加点。
5. 订单列表仍以 `curtain_pay_order` 为准，前端页面无需整体推翻。
6. 支付网关相关能力使用 `uni-pay 2` 承接，避免手写微信支付 v3 签名与验签主流程。

## 3. 非目标

本次不包含以下内容：

- 不重构现有套餐、点数、订单的数据模型。
- 不改造人工补点申请流程。
- 不在本次内实现完整退款能力，但会为后续退款预留字段和结构。
- 不将业务订单主表切换为 uni-pay 内部订单表。
- 不移除现有测试，而是在现有测试基础上扩展真实支付桥接测试。

## 4. 方案选择

### 4.1 备选方案

#### 方案 A：uni-pay 2 仅作为支付底座，业务订单继续使用 `curtain_pay_order`

特点：

- 保留现有 `curtain-pay-*` 业务云函数结构。
- 保留现有订单页、点数页和订单表。
- 真实微信下单、回调验签、查单由 `uni-pay 2` 承接。
- 支付成功后由业务回调更新 `curtain_pay_order` 与点数账户。

优点：

- 与现有代码贴合度最高。
- 风险最低。
- 后续扩展退款、补单、查单成本更低。
- 当前测试资产可继续复用。

缺点：

- 需要增加一层业务订单与支付订单的桥接关系。

#### 方案 B：全面切换到 uni-pay 订单体系

特点：

- 以 uni-pay 订单为唯一主订单。
- 业务表降级为扩展表或映射表。

缺点：

- 需要重构现有订单相关页面与测试。
- 改动大，不适合当前阶段。

#### 方案 C：手写微信支付 v3 下单与回调验签

缺点：

- 维护成本高。
- 容易出现签名、证书、回调验签错误。
- 与 DCloud 当前推荐实践不一致。

### 4.2 最终选择

本次采用 **方案 A**：`uni-pay 2` 负责支付底座，业务订单继续使用 `curtain_pay_order`。

## 5. 总体架构

### 5.1 业务分层

- 前端页面层：套餐展示、下单、拉起支付、支付结果提示。
- 业务订单层：`curtain-pay-order-create`、`curtain-pay-order-notify`、`curtain-pay-order-list`。
- 支付底座层：`uni-pay 2` 负责微信支付下单、回调、查单等网关能力。
- 点数账户层：`curtain_point_account`、`curtain_point_flow` 负责到账与流水。

### 5.2 核心原则

- 订单与余额以数据库状态为准，不以前端回调作为最终到账依据。
- 支付成功到账必须幂等。
- 业务订单状态与支付订单状态解耦，但通过唯一业务订单号进行关联。
- 支付底座替换不影响现有业务页面结构。

## 6. 数据流设计

### 6.1 下单流程

1. 用户在充值页选择套餐。
2. 前端调用 `curtain-pay-order-create`。
3. 服务端校验登录态与套餐有效性。
4. 服务端创建一条 `curtain_pay_order`，初始状态为 `init`。
5. 服务端调用 `uni-pay 2` 创建微信小程序支付单。
6. 服务端返回真实 `paymentParams` 给前端。
7. 前端调用 `uni.requestPayment` 拉起支付。

### 6.2 支付成功流程

1. 微信支付成功后触发支付回调。
2. `uni-pay 2` 完成回调验签与支付状态确认。
3. 进入业务到账逻辑。
4. 根据业务订单号查询 `curtain_pay_order`。
5. 若订单已是 `success`，直接跳过到账逻辑。
6. 若订单尚未到账：
   - 更新订单状态为 `success`
   - 写入 `transactionId`
   - 写入 `payTime`
   - 给 `curtain_point_account` 增加点数余额
   - 给 `curtain_point_flow` 写入一条充值流水

### 6.3 支付失败或取消

- 用户主动取消支付：前端提示“已取消支付”，不更新到账状态。
- 支付网关回调失败：业务订单状态更新为 `fail` 或保留 `init`，由后续查单策略兜底。
- 前端支付完成后页面中断：后续仍以服务端回调和订单查询结果为准。

## 7. 数据模型与字段策略

### 7.1 继续保留的表

- `curtain_point_package`
- `curtain_pay_order`
- `curtain_point_account`
- `curtain_point_flow`

### 7.2 `curtain_pay_order` 需要关注或补充的字段

当前已有：

- `uid`
- `packageId`
- `packageTitle`
- `orderNo`
- `amountFen`
- `points`
- `status`
- `payType`

建议补充或明确：

- `transactionId`：微信支付交易单号
- `payTime`：支付成功时间
- `payProvider`：建议固定为 `wxpay`
- `payChannel`：建议标识为 `mp`
- `thirdOrderNo`：支付底座订单号或外部单号映射
- `updateTime`：每次状态变化更新
- `failReason`：支付失败或回调失败原因（可选）

说明：

- 本次不要求重建 schema，但实现时应尽量兼容这些字段。
- 若表 schema 已有限制，应同步补充 schema 定义。

## 8. 前端改动设计

目标文件：`pages/profile/recharge.vue`

### 8.1 保留部分

- 套餐列表 UI 保留。
- 登录校验逻辑保留。
- 人工补点申请逻辑保持不变。

### 8.2 替换部分

将当前 mock 支付分支替换为真实支付分支：

- 创建订单成功后，不再弹出“模拟支付”确认框。
- 若服务端返回真实 `paymentParams`，前端直接调用 `uni.requestPayment`。
- 支付成功后：
  - 提示“支付成功，正在同步到账结果”
  - 刷新订单页入口或余额数据
- 支付取消后：
  - 提示“已取消支付”
- 支付失败后：
  - 提示真实错误信息

### 8.3 前端不承担的职责

- 前端不直接调用加点逻辑。
- 前端不自行判定订单最终到账。
- 前端不做余额推导。

## 9. 云函数改动设计

### 9.1 `curtain-pay-order-create`

职责：

- 校验用户登录状态。
- 校验套餐有效性。
- 创建业务订单 `curtain_pay_order`。
- 调用 `uni-pay 2` 发起微信小程序支付单。
- 返回真实支付参数。

设计要求：

- 业务订单先落库，再创建支付单。
- 支付单创建失败时：
  - 业务订单可保留为 `init` 或标记失败原因
  - 返回明确错误，便于前端提示
- 返回值中不再使用 `paymentParams.mock`。

### 9.2 `curtain-pay-order-notify`

职责：

- 接收支付成功后的业务到账处理。
- 保证重复调用不重复加点。

设计要求：

- 先查订单状态。
- 若已成功，直接返回成功并跳过重复处理。
- 若未成功，再执行订单更新、账户加点、流水写入。
- 订单更新和加点逻辑要尽量保持原子性；若当前环境不支持事务，至少要用“先判断状态再更新”的幂等顺序降低重复到账风险。

### 9.3 `curtain-pay-order-list`

职责：

- 保持当前用户维度的订单查询。
- 补充更稳定的状态展示字段。

状态建议：

- `init`：待支付
- `success`：支付成功
- `fail`：支付失败
- `closed`：已关闭（可选，后续补单或超时关闭时用）

## 10. uni-pay 2 接入设计

### 10.1 配置范围

需要在 `uniCloud-aliyun` 中完成 `uni-pay 2` 接入，并配置微信小程序支付节点。

关键配置项：

- 小程序 `appId`
- 小程序 `appSecret`
- 微信商户号 `mchId`
- API v3 密钥
- 商户 API 证书私钥
- 商户证书序列号
- 小程序支付渠道配置 `wxpay.mp`

### 10.2 使用方式

- 支付网关能力统一交给 `uni-pay 2`。
- 业务订单号 `orderNo` 作为主业务标识。
- `uni-pay 2` 的下单请求中需要带上业务订单号和金额。
- 回调中要能反查到业务订单号。

### 10.3 环境约束

- 真实支付依赖正式商户配置。
- 开发过程中代码可先接通，但无配置时不能声称已完成真实支付冒烟。
- 正式环境与测试环境配置必须分离，避免误用正式商户参数。

## 11. 幂等与一致性设计

### 11.1 幂等目标

同一业务订单无论收到多少次支付成功通知，都只能加点一次。

### 11.2 幂等策略

- 以 `curtain_pay_order.status === 'success'` 作为已到账判断。
- 支付通知到达时先查订单：
  - 已成功：直接返回成功
  - 未成功：继续执行到账
- 点数流水 `bizType = order` 且 `bizId = orderNo`，便于后续核查

### 11.3 一致性策略

- 订单状态与余额流水以服务端写库结果为准。
- 前端 success 仅代表“客户端支付动作完成”，不代表最终业务到账。
- 若出现前端成功但服务端回调未落库，可通过后续查单或补单策略兜底。

## 12. 测试设计

### 12.1 保留现有测试目标

继续保留现有覆盖：

- 创建订单写入业务订单
- 回调成功后加点幂等
- 当前用户订单列表筛选正确

### 12.2 需要新增的测试点

1. `curtain-pay-order-create` 在真实支付模式下返回非 mock 的支付参数结构。
2. 订单创建后能保存支付桥接所需字段。
3. 重复回调不会重复写点数流水。
4. 支付失败回调会更新订单失败状态。
5. 前端支付成功后不直接加点，到账必须依赖服务端业务回调。

### 12.3 验收方式

自动化验收：

- `node --test tests\curtain-payment-cloud.test.js`

人工验收：

1. 登录小程序
2. 打开充值页
3. 选择套餐并拉起微信支付
4. 完成支付
5. 回到个人中心检查：
   - 点数余额增加
   - 点数流水新增充值记录
   - 订单列表新增成功订单

## 13. 风险与缓解

### 13.1 商户配置风险

风险：

- 商户号与小程序未正确绑定
- API v3 密钥或证书配置错误
- 正式环境参数误填到测试环境

缓解：

- 将支付配置集中管理
- 明确区分环境
- 冒烟前先做配置清单核对

### 13.2 回调不到账风险

风险：

- 支付成功但服务端回调链路未正确落库

缓解：

- 保留订单查询与后续补单能力的扩展口
- 通过订单状态与流水交叉核查异常单

### 13.3 重复到账风险

风险：

- 支付成功通知重复触发导致重复加点

缓解：

- 服务端以订单状态作为幂等门禁
- 测试覆盖重复通知场景

## 15. 最终结论

本次真实微信支付接入采用：

- **支付底座：`uni-pay 2`**
- **业务主订单：`curtain_pay_order`**
- **到账依据：服务端回调**
- **点数变更依据：业务订单成功状态 + 点数流水**

这样可以在尽量少改现有业务页面和数据结构的前提下，完成真实微信支付接入，并为后续退款、补单、查单保留扩展空间。
